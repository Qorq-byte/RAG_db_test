# 下一阶段实施计划：旧向量索引显式清理

## 状态与依据

**状态：6.1–6.4 开发与验收已完成（2026-09-26），文档推送后合并主线。** 最终全量回归 249 passed，CLI、Windows 原生桌面与 `ragdb doctor` 通过；结果与底层 Chroma 间歇性读取限制见[阶段 6 验收](../../acceptance/2026-09-26-vector-index-maintenance.md)。用户已授权执行本计划；本阶段边界见[维护设计](../specs/2026-09-25-vector-index-maintenance-design.md)。

[模型设置设计](../specs/2026-09-24-desktop-model-settings-design.md)要求重建成功后保留旧 Chroma 命名空间，并将清理留给后续显式维护流程。`ChromaVectorStore` 按 `ragdb_<集合 UUID>`（legacy）或 `ragdb_<集合 UUID>_<指纹前 24 位>` 命名集合；SQLite `active_embedding_profile.namespace_id` 是活动索引的权威来源。本阶段实施前只有按已知集合与命名空间删除的方法；现已补齐盘点和确认清理入口。

## 目标与边界

- 先列出明确属于本项目且已停用的向量集合、所属知识集合、命名空间和向量条数；预览不修改存储。
- 用户查看预览并明确确认后，才按预览的精确目标清理；再次执行应安全地报告无待清理项。
- 清理期间和清理前后始终保护 SQLite 当前活动命名空间；资料、FTS、当前向量、聊天配置与系统凭据不受影响。
- 本阶段只处理能同时通过命名规则、SQLite 集合 UUID 和 Chroma 元数据核验的已停用向量集合。无法确认归属、元数据缺失、集合已从 SQLite 删除或命名不符合规则的对象仅报告为“需人工核查”，不提供强制删除。
- 不做自动后台清理，不清理整个 Chroma 目录，不承诺精确释放字节数。旧索引一经清理，不能再直接依赖它回退；需要时须重新生成向量。

## 实施步骤与单步交付

### 6.1 安全边界与只读盘点

1. 在向量存储适配层增加只读集合枚举，返回集合名、元数据和向量条数；不通过构造路径删除 Chroma 内部文件。
2. 在应用服务中读取 SQLite 已登记的集合与活动 `namespace_id`，只把名称、UUID、元数据均匹配且不是当前活动名称的项目向量集合列为清理候选。将无法确认的对象单列展示，避免误删其他数据。
3. 以候选集合精确名称和当前活动 profile 生成预览标识；零候选时返回空结果。测试覆盖 legacy、指纹命名空间、多个集合、活动索引、陌生对象及缺失元数据。
4. 定向测试通过后提交并推送本阶段工作分支；更新[交付记录](../../../progress.md)。

### 6.2 显式预览入口

1. 在 CLI 增加只读预览命令，显示候选集合、命名空间、向量条数和预览标识；明确说明“条数不是可释放字节数”。
2. 在桌面“任务与诊断”增加“索引维护”视图：后台执行盘点，显示活动索引与可清理对象，并列出无法确认的对象；盘点失败给出可操作错误。首次打开与刷新均不修改数据。
3. 测试 CLI 输出、桌面空状态/错误状态/候选展示以及后台防重复提交。定向测试通过后单独提交并推送。

### 6.3 受保护的清理执行

1. CLI 执行命令须提供预览标识和明确确认参数；桌面须在列出精确目标和旧索引不可直接回退的提示后得到用户确认。两端复用同一应用服务。
2. 服务先取得现有 SQLite 跨进程互斥门禁，再读取活动 profile、重新盘点和比对预览标识；目标或活动 profile 变化时拒绝执行并要求重新预览。删除前再次排除当前活动集合；使用 Chroma 集合 API 按精确名称逐个删除。
3. Chroma 与 SQLite 无共同事务。若部分删除失败，记录已清理与未清理的集合名，保留活动索引，释放门禁；再次盘点后可重试。禁止把密钥、切片文本或整份资料内容写入日志。
4. 在隔离临时数据目录测试重建后清理、活动索引仍可检索、预览过期、与重建/导入竞争、部分故障重试和重复执行。定向测试通过后单独提交并推送。

### 6.4 文档与最终验收

2. 在隔离合成集合完成 CLI 与 Windows 原生桌面流程检查；运行全量 pytest、`ragdb doctor` 和文档链接检查。旧索引清理测试不操作用户实际资料库。
3. 将命令、测试结果和剩余限制写入独立验收记录，更新[进度总览](../../../task_plan.md)与[交付记录](../../../progress.md)。逐步推送后按用户既有要求合并 GitHub `main`。

## 完成标准

- 预览只报告可证明归属且已停用的集合；活动、陌生和证据不足的集合不会进入执行目标。
- 预览与执行之间发生配置或集合变化时，执行被拒绝；已有导入或重建占用门禁时不会清理。
- 成功清理后当前模型检索仍可用；失败、重复执行及进程重启后可以重新盘点并安全重试。
- CLI、桌面定向测试与全量回归通过；每一步有独立提交和推送，最终验收与主线合并记录可追溯。

# 下一阶段规划：索引重建与读取可靠性（阶段 7）

## 状态与依据

**状态：实施中，7.1 完成；7.2–7.4 待实施。** 本文是基于当前交付证据整理的推荐执行路线，具体底层修复以 7.1 的调查结果为准。调查结果见 [阶段 7 验收记录](../../acceptance/2026-09-26-index-reliability.md)。

基线为 GitHub `main` 的 `3cbdc9b`：阶段 6 已通过 `15d16e7` 合并，最终回归 249 passed，CLI、Windows 原生桌面与 `ragdb doctor` 通过，详见[验收记录](../../acceptance/2026-09-26-vector-index-maintenance.md)。当前模型组合继续使用本地 Ollama `embeddinggemma:latest` 嵌入和 DeepSeek `deepseek-flash` 问答/学习生成。

阶段 6 中曾发生 Chroma `Nothing found on disk`，重建模块独立复核及最终全量回归通过，但根因尚未确定。现有清理在活动索引不可读时拒绝删除；现有重建发布前主要通过 `has_chunks()` 校验切片 ID，没有独立证明所有新集合都能执行向量查询。

另外，维护适配器已按操作关闭客户端；`ChromaVectorStore` 尚无显式关闭接口，runtime 每次构造嵌入上下文会新建适配器。是否存在长期资源增长，需要测量后判断，不能把它直接认定为读取错误的原因。

## 优先级选择

| 路线 | 收益与代价 | 安排 |
| --- | --- | --- |
| 索引可靠性 | 直接承接已观察到的读取异常及发布校验缺口；需要隔离复现和故障测试 | 推荐作为阶段 7 |
| 全库备份与恢复 | 提高恢复能力；涉及 SQLite、Chroma、原始文件和凭据的边界，工作范围更大 | 后续单独规划 |
| 检索效果评估与调优 | 可衡量召回质量；需要代表性语料及答案标注 | 后续单独规划 |

## 目标与边界

- 明确读取异常的触发条件；有证据时修复，证据不足时记录未知项和保守处置，不能以偶然通过宣称根因解决。
- 新嵌入索引只有在切片校验与实际向量查询校验均通过后才能发布；失败或取消时旧 profile、旧索引及 FTS 保持可用。
- 明确向量客户端的所有者、共享范围和释放时机，避免关掉仍被后台任务使用的客户端。
- 保持阶段 6 的预览确认、互斥门禁、活动索引保护和失败重试行为。
- 全部写入、故障注入与清理验证使用隔离合成库；日志只记录必要的错误类别、数量、版本和阶段，不含密钥、正文或向量内容。

本阶段不包含自动删除旧索引、直接修补 Chroma 内部文件、备份恢复、检索算法调优或新模型接入。现有同 profile 重建会提前返回，不应为修复异常而先删除活动命名空间；如证据显示需要同模型修复入口，应另行设计独立暂存命名空间和原子发布方案。

## 分步实施与交付

### 7.1 复现与归因

1. 记录本机 Python、Chroma 和锁文件版本；将错误发生时的操作顺序与当前实现对照。
2. 建立最小合成复现：默认参数下的微型索引、多个集合、逐条与批量写入、写后查询、客户端关闭重开、独立进程重开。对比单测与全套测试资源累积，避免同时修改多个变量。
3. 对已发现的差异进行固定规模复核，记录总次数、失败次数、阶段和耗时；不以重复运行直到通过作为验证。
4. 区分持久化、客户端生命周期、测试污染或依赖版本问题。只有证据支持才调整依赖或增加针对已确认瞬态错误的有界等待；持久损坏、权限错误、维度错误须直接报告。
5. 输出调查记录和回归复现用例；未复现也须记录覆盖条件与未确定结论。提交并推送该步骤。

**完成标准：** 调查可复跑，现象与推断分开；下一步的修改范围有证据依据，不更改用户库。

### 7.2 客户端生命周期与针对性修复

1. 在 `ChromaVectorStore` 确立幂等关闭或上下文管理契约，明确 CLI 短任务、桌面后台任务和重建服务的所有者。
2. 沿实际调用链处理资源释放；后台任务完成后释放，异常/取消也释放。共享同一存储系统时，一个所有者退出不能影响其他使用者。
3. 依据 7.1 实施最小修复；若需修改依赖版本，先在隔离环境核对兼容性并更新锁文件，保留回退方法。
4. 验证重复创建/使用/释放后引用回到基线、两个同时存活的使用者互不影响、独立进程重开后可读。Windows 句柄趋势作为辅助证据，不用易波动的绝对值作唯一断言。
5. 定向回归通过后独立提交推送；技术发现记录根因、证据及剩余限制。

**完成标准：** 所有涉及路径的释放责任明确；故障路径不遗留自身资源，仍在运行的任务不被误关。

### 7.3 发布前验证新索引可查询

1. 保留逐批切片 ID 校验；在 `profiles.activate()` 之前，对每个实际写入的目标集合执行一次真实向量查询，使用本轮已有向量或存储中的向量，不为校验追加模型请求。
2. 验证结果非空且来自预期集合与当前资料代次。允许相同向量产生并列结果，不要求采样 ID 一定排名第一；空知识集合按无需向量处理。
3. 在现有独占门禁内完成校验与发布，校验间检查取消；任何未通过的集合阻止全局发布，并沿用暂存清理与旧 profile 保留逻辑。
4. 若 7.1 证明存在可恢复的短暂不可读，等待策略必须有明确总时限并支持取消；只处理已确认错误类型，超过时限即失败，不隐藏其他异常。
5. 增加注入用例：ID 存在但查询失败、空/错误结果、多集合中一项失败、校验期间取消、成功发布与独立进程重开查询。定向通过后提交推送。

**完成标准：** 所有非空新集合校验通过才发布；失败和取消均不切换活动 profile，旧索引可检索，模型调用数量不因校验额外增加。

### 7.4 联合验收、使用说明与合并

1. 隔离流程覆盖“重建 → 读取验证 → 发布 → 进程重开 → 检索 → 预览清理旧索引 → 再次检索”，核对 SQLite 与 FTS。
2. CLI 与 Windows 原生桌面核对成功、校验失败、取消后重试文案及任务结束状态；没有已验证的清单不能开始清理。
3. 执行全量 pytest 和 `ragdb doctor`，记录命令、版本、结果及失败。只有存在具体残余风险才追加重复测试。
4. 更新 README、进度总览、交付记录和独立验收文档；列明底层错误是否已证明解决、是否仍有残余限制。
5. 每个完成步骤单独提交推送；本阶段完成后按既有交付约定合并 GitHub `main`，核对远端和用户已有文件。

**完成标准：** 新增回归与全量回归通过，失败/取消保护得到验证，证据可追溯；未解决问题如实登记，不能标为已修复。
